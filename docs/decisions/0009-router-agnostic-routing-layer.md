# 0009. ルーターを差し替え可能な層に閉じ込める

- 状態: Accepted
- 日付: 2026-07-27

## 背景

`apps/web`は単一ページで、ルーターを持っていませんでした。
ページを増やすにあたりルーターが必要ですが、React Routerと
TanStack Routerのどちらを長期的に使うかは決めきれていません。

ルーターのAPIをcomponentへ直接書くと、乗り換えのたびに
`useNavigate`、`<Link>`、`useSearchParams`の呼び出し箇所すべてを書き換えることになります。
その規模は、ルーターを選び直す判断自体を難しくします。

## 決定

ルーティングをportとadapterに分けます。
アプリは`NavigationPort`（`location`と`navigate`のみ）に依存し、
具体的なルーターは`src/routing/adapters/<router>/`に閉じ込めます。
既定のアダプタはReact Routerです。

## 理由

- 乗り換えの影響範囲が、アダプタ1ディレクトリと`main.tsx`に限定されます。
- portが小さいほど、どのルーターでも満たせます。
  `location`と`navigate`は、あらゆるルーターが提供する最小公倍数です。
- ルート定義を**importを持たないデータ**として切り出すと、
  実行時のルーターとビルド時のHTML生成の両方から同じ定義を読めます。
- search paramsをzodで検証することで、
  ルーター固有の型システムに依存せずに型と実行時の安全性を得られます。
- テスト用のin-memoryアダプタを用意でき、
  componentのテストがルーターの初期化を必要としません。

## 検討した代替案

- **ルーターを直接使う**: 最も素直で、各ルーターの機能をすべて使えます。
  今回は「どちらを使うか未定」という前提が合いませんでした。
- **ルーターを入れない**: ページが増えるたびに自前の分岐が育ちます。
  履歴、スクロール復元、リンクの扱いを自分で正しく実装する負担が残ります。
- **両ルーターを常時併存させる**: 差し替え可能性は最も強く保証されますが、
  実装量と依存が2倍になり、日常の開発コストに見合いません。

## 結果

`pages/`、`features/`、`components/`はルーターを知りません。
これは`src/routing/routing-boundary.test.ts`が機械的に検証します。

引き受けたトレードオフです。

- ルーター固有の機能（loader/action、型安全なパスパラメータ、プリフェッチ）は
  portの外側にあります。使いたくなった時点で、
  portを広げるか、移植性を諦めるかを明示的に判断します。
- 共通`Link`を自前で持つため、クリック時にブラウザへ委ねる条件
  （修飾キー、`target`、副ボタン）を自分で正しく扱う必要があります。
  `link-behavior.ts`に切り出してテストしています。

ルーターの選択が確定し、その固有機能に本格的に依存すると決めた場合は、
このADRを置き換えてportを外すことを検討します。
