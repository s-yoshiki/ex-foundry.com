# 0010. 1つのAWSアカウントに命名で複数環境を共存させる

- 状態: Accepted
- 日付: 2026-07-27

## 背景

`apps/api`をAWSへデプロイするにあたり、`dev`と`prd`を分ける必要があります。
一般的な構成は環境ごとにAWSアカウントを分ける方式ですが、
個人プロジェクトの規模ではOrganizations、アカウント間のIAM、
請求の分離といった運用が本体の作業量を上回ります。

同一アカウントに複数環境を置く場合、リソース名の衝突が最大の事故要因です。
名前を持つリソース（Lambda関数、ロググループ、CloudFormation export）は
アカウント・region内で一意である必要があり、
1か所でも環境名を含め忘れると2つ目の環境のデプロイが壊れます。

## 決定

1つのAWSアカウントに`dev`と`prd`を共存させます。
分離はIAMではなく**命名規約**で行い、その規約を
`src/naming.ts`の関数に集約してテストで守ります。

環境は`cdk -c env=<name>`で指定し、デフォルト値を持ちません。

## 理由

- 命名を関数に閉じ込めれば、衝突の可能性がある箇所が1ファイルに限定されます。
  文字列を手で組み立てる限り、いずれどこかで環境名が抜けます。
- 環境ごとの差分（メモリ、ログ保持、削除ポリシー）を
  `environments.ts`のテーブルに集約すると、
  stackのコードから環境分岐が消えて読みやすくなります。
- 環境指定にデフォルトを置かないことで、
  「フラグを忘れて本番へデプロイした」という失敗が構造的に起きません。
- regionをコードに固定することで、
  実行者のAWSプロファイルによってデプロイ先が変わりません。
- CDKのテストは合成したテンプレートに対して行うため、
  AWSへ接続せずにCIで検証できます。

## 検討した代替案

- **環境ごとにAWSアカウントを分ける**: 分離は最も強く、
  誤操作が別環境へ波及しません。この規模では運用コストが見合いません。
  規模が大きくなった場合はこちらへ移行すべきです。
- **1つのstackにdev/prd両方のリソースを定義**: デプロイは1回で済みますが、
  devの変更がprdのstackを更新対象にしてしまい、変更の影響範囲が読めなくなります。
- **環境名を含む変数を各所で組み立てる**: 命名関数を作らない案です。
  抜け漏れをレビューで防ぐ前提になり、事故が起きるまで気づけません。

## 結果

同一アカウントである以上、IAMによる分離はありません。
devの操作ミスがprd由来のリソースに触れうる点は残ります。
これを緩和するため、prdには削除保護と`RemovalPolicy.RETAIN`を設定しています。

状態を持つリソースを追加する際は、必ず`environment.removalPolicy`を渡してください。
prdの誤削除を防ぐ仕組みはここにしかありません。

環境が3つ以上に増える、あるいは扱うデータの重要度が上がった時点で、
アカウント分離へ移行する判断を再検討します。
