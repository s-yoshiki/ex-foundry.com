# 0003. フロントエンドをfeature単位で分割する

- 状態: Accepted
- 日付: 2026-07-27

## 背景

`components/` `hooks/` `utils/`のように技術種別で分割すると、
1つの機能を変更するために複数のディレクトリを行き来することになります。
機能の削除も難しく、どのファイルが誰に使われているか追いにくくなります。

## 決定

`apps/*/src/features/<feature>/`にユーザーが認識できる機能単位で分割し、
その内側を`components` / `hooks` / `functions` / `types`に分けます。
featureに属さないアプリ全体の骨組みは`src/components/`へ置きます。

## 理由

- 1つの機能に関するコードが1つのディレクトリに集まるため、
  変更範囲と削除範囲が一致します。
- 依存の向きを`components → hooks → functions → types`に固定すると、
  純粋なロジックがReactから独立し、単体でテストできます。
- `utils`のような曖昧な置き場を作らないことで、
  「とりあえずここへ置く」という判断を防げます。

## 検討した代替案

- **技術種別で分割**: 小規模なうちは動きますが、
  機能が増えるほど1機能あたりの変更点が散らばります。
- **完全にフラット**: ファイル数が増えると探索性が落ちます。

## 結果

すべてのディレクトリを最初に作る必要はありません。
責務が発生した時点で追加します。

feature間の直接importが増えてきたら、共有packageかapp-levelのmoduleへ
切り出すサインとして扱います。
`pnpm create:feature`が、この構造の雛形を生成します。
