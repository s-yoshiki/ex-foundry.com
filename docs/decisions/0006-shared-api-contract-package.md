# 0006. APIインタフェースを専用packageで共有する

- 状態: Accepted
- 日付: 2026-07-27

## 背景

`apps/api`と`apps/web`が同じリポジトリにあっても、
レスポンスの形を各自で定義すると実装が静かに食い違います。
型だけを共有しても、デプロイ済みAPIが古い場合に
クライアントは「型どおりのはず」のデータでクラッシュします。

Honoには`hc<AppType>`によるRPCがありますが、
これはクライアントがサーバー実装の型をimportすることを意味し、
`apps/web` → `apps/api`というapp間の依存が生まれます。

## 決定

`packages/api-contract`を新設し、ルート定義とzodスキーマを両側で共有します。
サーバーは入力の検証に、クライアントはレスポンスの検証に同じスキーマを使います。

## 理由

- 依存方向がapp → packageに保たれ、app間の依存が生まれません。

  ```text
  apps/api ──▶ packages/api-contract ◀── apps/web
  ```

- zodスキーマは型とランタイム検証の両方を1つの定義から提供します。
  型定義とバリデーションを二重に書く必要がありません。
- ルート定義を共有することで、パスのrenameが両側のビルドエラーになります。
- クライアント側でもレスポンスを検証するため、
  コントラクトのずれが「不明な箇所でのクラッシュ」ではなく
  「扱えるエラー」になります。

## 検討した代替案

- **Hono RPC（`hc<AppType>`）**: 型の追従は最も自動化されますが、
  app間依存を生み、ランタイム検証は提供されません。
- **型定義だけを共有**: 実行時のずれを検出できません。
- **OpenAPIから生成**: 仕様の管理コストがこの規模には見合いません。
  APIが外部公開されるなら再検討します。

## 結果

APIの変更は、コントラクト → サーバー → クライアントの順に進めます。
`pnpm typecheck`と`pnpm test`が両側の整合を検証します。

`apps/web`は`VITE_API_BASE_URL`が未設定なら一切APIを呼ばないため、
静的サイトとしてのビルドはAPIの有無に影響されません。
